Chapter 01

The whole flow in one picture

Before: you wrote code, committed, and pushed straight to main. Now there is one extra stop between your code and main: a pull request, where a robot runs the checks and you look at the result before it goes in.

  H -- "looks good" --> I["Merge into main"]
Everything left of "Merge" happens on a separate branch, so main only ever receives finished, checked work.

The rest of this handbook explains each box. If you only remember three things:

  • A branch is a separate line of work, so unfinished code never lands on main.
  • A pull request is a request to merge a branch into main. It's where checks run and where you review.
  • CI is a robot on GitHub's servers that runs type checks, lint and tests on every pull request, so you don't have to remember to.
Chapter 02

Git basics, compared to what you do today

Git keeps the full history of your project as a chain of snapshots. Each snapshot is a commit. The copy on GitHub is called the remote, and git nicknames it origin. Your laptop has its own full copy of the repository with its own history.

What you do today

  • Edit files in ~/codes/ERP-diecast
  • git add . and git commit -m "…"
  • git push sends your commits to main on GitHub
  • git pull brings other people's commits down
  • Everyone works on main directly

What changes

  • Same commands, but on a branch instead of main
  • git push sends the branch to GitHub
  • You open a pull request to merge it
  • CI checks it; you merge it on GitHub
  • Then git pull on main, as before

The four places your code can be

PlaceWhat it isHow code gets there
Working folderThe files you see and edit on diskYou type
Staging areaChanges you've marked for the next commitgit add
Local historyCommits saved on your laptopgit commit
Remote (origin)The copy on GitHub everyone sharesgit push (and git pull to bring it back)

Commands you'll see, in plain words

git log --onelineLists recent commits, one per line. The 7-character code at the start (e.g. ffa1255) is the commit's ID.

Chapter 03

Branches

Analogy

main is the approved drawing of a die. A branch is a photocopy you mark up while designing a change. The approved drawing stays clean until your markup is checked and accepted. Then the changes are copied onto it (that's a merge).

A branch is just a name pointing at a chain of commits. When you create one, it starts as an exact copy of where you were (usually main). Commits you make on it don't affect main at all until you merge.

gitGraph
  commit id: "68941a7"
  branch worktree-workflow-setup
  checkout worktree-workflow-setup
  commit id: "a29819d workflow"
  commit id: "0a406f4 pipeline"
  commit id: "b17de0e knowledge"
  commit id: "5681c94 CI green"
  checkout main
  merge worktree-workflow-setup id: "ffa1255 merge PR #1"
This is exactly what happened with PR #1: five commits on a branch, then one merge commit (ffa1255) that brought them into main.

Why bother

  • main always works. The factory will eventually run what's on main. Half-finished GRN changes never reach it.
  • Several things at once. A GRN fix and a BOM feature can be in progress on two branches without mixing.
  • Easy undo. If an idea doesn't work, delete the branch. main never saw it.

Branch commands

$ git switch main                 # go to main
$ git pull                        # make sure it's up to date
$ git switch -c feature/grn-fix   # create a new branch from here and move onto it
  … edit, git add, git commit as usual …
$ git push -u origin feature/grn-fix   # first push of a new branch (-u links it to GitHub)
$ git push                        # later pushes on the same branch
$ git branch                      # list your branches; * marks the current one
$ git branch -d feature/grn-fix   # delete it after it's merged

Chapter 04

Pull requests (PRs)

A pull request is a page on GitHub that says "please merge branch X into main". It shows every changed line, runs the CI checks, and has a place for comments. Nothing happens to main until someone presses Merge. For this repo, that's you.

Life of a PR

  1. Openagent or you

    After pushing a branch: gh pr create, or the "Compare & pull request" button GitHub shows.

  2. Checks runGitHub

    CI starts automatically. The PR shows a yellow dot (running), a green tick (passed) or a red cross (failed).

  3. Reviewyou

    Read the description (the pipeline writes what changed and a manual test checklist), try it in the UI, and leave comments on specific lines if something's wrong.

  4. Fixagent

    New commits pushed to the same branch appear in the same PR automatically, and CI runs again.

  5. Mergeyou

    Press Merge pull request. GitHub creates a merge commit on main. The PR is closed and marked "Merged".

  6. Tidy upyou or /watch-prs

    Delete the branch (GitHub offers a button), and run git pull on main locally.

What the PR status words mean

You seeMeaningWhat to do
✅ All checks have passedCI ran and everything is greenTest in the UI, then merge
❌ Some checks were not successfulA CI job failed (type error, lint error or failing test)Click "Details" to see which step and why; don't merge until fixed
🟡 Some checks haven't completed yetCI is still running (usually 1–2 minutes here)Wait
"This branch has conflicts"Someone changed the same lines on main since the branch startedSee What if… → merge conflict
Merge button enabled while redOn GitHub Free with a private repo, checks can't be made mandatoryIt's on you not to merge red PRs
What happened with PR #1

Its checks went red at first. That wasn't because of the PR's own changes: it added CI for the first time, and CI found problems that were already on main but that nobody had been checking (a half-finished rename in the approval form, a formatting error, lint errors). They were fixed on the same branch, CI went green, and then it was merged.

Chapter 05

Worktrees

This is the part that's usually confusing, because it's not something you need when you work alone in one folder.

Analogy

Normally, one folder shows one branch at a time. git switch swaps every file in the folder to the other branch. A worktree is a second folder attached to the same repository, showing a different branch. It's like having a second desk with a different drawing laid out, both drawings coming from the same filing cabinet.

~/codes/ERP-diecast/ ← your main folder (branch: main) ├── .git/ ← THE repository: all history, all branches (one copy) ├── backend/ frontend/ docs/ … ← files of branch "main" └── .claude/worktrees/ ├── dev-foundation/ ← worktree 2 (branch: feature/dev-foundation) │ └── backend/ frontend/ docs/ … ← full set of files for THAT branch └── grn/ ← worktree 3 (branch: feature/grn) └── backend/ frontend/ docs/ …

Why the agent pipeline needs them

  • Agents and you don't collide. While an agent edits backend/ for feature/grn in its worktree, your main folder is untouched. Your own half-done edits don't leak into the agent's work, and the other way round.
  • Parallel features. Two pipelines can run at once, one folder each.
  • No switching cost. With one folder, git switch would change files under a running dev server or an agent mid-edit. With worktrees nobody has to switch.

Things that are true about worktrees

  • There's still only one repository. All folders share the single .git. A commit made in a worktree is instantly visible from your main folder (git log feature/grn). Nothing is copied or synced.
  • Each folder is a full checkout. It has every file, and it needs its own bun install (its own node_modules) and its own .env if it runs the app. That's why they use disk space.
  • A branch can only be open in one folder at a time. If feature/grn is open in a worktree, you can't also git switch feature/grn in your main folder.
  • Why inside .claude/: it's where Claude Code creates worktrees by default, and the pipeline follows that. The folder is hidden from git by a local ignore rule (.git/info/exclude contains **/.claude/worktrees/), so worktrees never show up as "changes" and are never committed.
  • They don't go away on merge. Merging a PR changes main on GitHub only. The worktree folder stays until it's removed (the pipeline's /watch-prs removes it after a merge; otherwise you do).

Worktree commands

$ git worktree list                                 # show all folders and their branches
$ git worktree add -b feature/x .claude/worktrees/x main   # new folder + new branch from main
$ cd .claude/worktrees/x                            # work there like any folder
$ git -C .claude/worktrees/x status --short         # check a worktree without cd-ing into it
$ git worktree remove .claude/worktrees/x           # delete the folder (refuses if it has uncommitted work)
$ git branch -d feature/x                           # delete the branch too, once merged
You don't have to use them yourself

For your own manual work, the plain branch flow from Chapter 03 in your main folder is enough. Worktrees are mainly for the agents. You'll only really touch them to cd into one and run the app when testing a PR, or to remove a leftover one.

Chapter 06

CI: the robot that checks every PR

CI stands for Continuous Integration: every time code is about to be merged, a machine automatically builds and checks it. On GitHub this is done by GitHub Actions.

Where it's configured

One file: .github/workflows/ci.yml at the repo root. GitHub looks in .github/workflows/ of every repository and runs any YAML file it finds there. There's no setting to turn on and no server of your own. Committing the file is the whole setup.

Where it runs

On GitHub's machines, not your laptop. For each run, GitHub starts a fresh, empty Linux virtual machine (ubuntu-latest, called a runner), downloads your code, runs the steps, reports the result, and throws the machine away. Your Docker, your database and your laptop being on or off make no difference. The free plan includes a monthly allowance of minutes for private repos (check GitHub → Settings → Billing); one run of this repo takes about a minute.

When it runs

The top of the file says:

on:
  pull_request:          # every time a PR is opened or gets new commits
  push:
    branches: [main]     # and every time main itself changes (e.g. after a merge)

What it runs: the file explained

A workflow has jobs (they run in parallel, each on its own machine), and each job has steps (they run in order; the first failing step stops the job).

JobStepWhat it proves
backend
with a Postgres 15 service container, a throwaway database started just for this job		checkout, setup-bunGets your code and installs Bun
bun install --frozen-lockfileDependencies install exactly as locked in bun.lock
bun run typecheckNo TypeScript errors (tsc --noEmit)
bun run lintBiome finds no errors (formatting, unused imports, risky code)
Schema + seedDrizzle schema can be created on an empty DB; seed_page_access.sql runs cleanly
bun testAll backend tests pass against that database
contract:generateThe API contract (list of 82 endpoints) can be generated
frontendcheckout, setup-bun, installSame as above
bunx tsc --noEmitNo TypeScript errors in the Next.js app
bun run lintBiome finds no errors

The fake secrets in the file (ci-access-token-secret-…) are only there because the backend refuses to start without secrets. They exist only inside that throwaway machine and protect nothing.

How to see results

  • On the PR page: the checks box near the bottom → Details next to a job → click the failed step (red cross) to read its output.
  • Actions tab of the repo on GitHub: every run, for every branch.
  • Terminal: gh pr checks 1 (status of PR #1), gh run list, gh run view <id> --log-failed (only the failing lines).

Running the same checks on your laptop first

$ cd backend  && bun run typecheck && bun run lint && bun test
$ cd frontend && bunx tsc --noEmit && bun run lint
$ bunx biome check --write .     # auto-fix formatting and import order
CI vs CD

You'll also hear CD (Continuous Delivery/Deployment): automatically deploying after checks pass. This repo has CI only. Nothing is deployed automatically.

How a test file looks

Tests live in backend/tests/, in the same folders as src/ (routes, service, …), as *.test.ts. bun test finds every such file and runs it.

// backend/tests/service/grnService.test.ts (example of the style agents will write)
import { test, expect } from "bun:test";

test("BR-GRN-04 rejects received qty above PO open qty", async () => {
  // arrange: create a TEST_ supplier, item, PO with 100 open
  // act:     try to receive 120
  // assert:  it throws the right error and posts nothing to inventory_ledger
});

Naming each test after its rule id (BR-GRN-04) links the spec, the test and the code. When a test fails, you know exactly which business rule broke.

Chapter 08

The local database and Docker

The backend needs PostgreSQL. You don't install Postgres on your Mac. You run it inside Docker.

  • Docker runs small isolated "mini-computers" called containers. Docker Desktop is the Mac app that runs them; it must be open.
  • Docker Compose starts containers described in a file. backend/docker-compose.yaml describes one: Postgres 15, database diecast, on port 5432.
  • docker compose up -d (in backend/) starts it in the background. Your data lives in a Docker volume and survives restarts.

Getting the database ready

Command (in backend/)What it does
docker compose up -dStart Postgres
bun run db:pushSchema push: Drizzle compares your TypeScript schema files with the database and creates/alters tables to match
psql … -f src/db/seed_page_access.sqlSeed: inserts starter data (roles, pages, who sees which page)
bun scripts/seed-approval-policies.tsSeeds approval rules (needs a super-admin employee to exist)
bun run db:reset (planned, BL-005)One command: wipe, push schema, seed everything, add realistic test data and a login per role
Who needs a database, when

CI creates its own throwaway one on GitHub. You do nothing. Pipeline agents start the Docker one when they run tests, so keep Docker Desktop open during a /feature run. You need it only to click through a PR in the browser. Once db:reset exists (the dev-foundation feature), that's a single command.

Migrations vs push: today the schema is applied with db:push ("make the DB look like the code"). Before the factory has real data, this switches to migrations: numbered SQL files that record each change, so production data is upgraded safely and reviewably (decision D-004, backlog BL-011).

Chapter 09

The .claude folder

.claude/ folders hold instructions and configuration for Claude Code. The app is plain code; these files only change how Claude behaves in this repo. There are three of them, and where each one sits decides when Claude reads it.

ERP-diecast/ ├── CLAUDE.md ← always read: how work flows, the rules, where docs live ├── .claude/ ← ROOT: the workflow layer, for the whole repo │ ├── settings.json ← permissions: what Claude may run without asking (shared, committed) │ ├── settings.local.json ← your personal extra permissions (not committed) │ ├── agents/ ← pipeline agents: explorer, backend-dev, frontend-dev, reviewers, test-runner… │ ├── skills/ ← your commands: /spec /freeze /feature /epic /watch-prs /status /map /bug /wrap │ ├── pipeline/PROTOCOL.md ← how agents hand work to each other │ └── worktrees/ ← agent work folders (git-ignored locally) ├── backend/ │ ├── CLAUDE.md ← read when working on backend files: Hono/Drizzle conventions │ └── .claude/ ← BACKEND layer: backend-only agents and skills │ ├── agents/ ← hono-builder, hono-reviewer (detailed backend rules) │ └── skills/ ← api-endpoint-intake, pagination-contract… └── frontend/ ├── CLAUDE.md ← read when working on frontend files: Next.js 16 conventions └── .claude/ ← FRONTEND layer ├── agents/ ← nextjs-builder, nextjs-reviewer └── skills/ ← data-table, ui-form-standards, structure-guard…

Why some things are at the root and others aren't

Lives inBecause it's aboutExamples
Root .claude/The process: spans backend and frontend (specs, PRs, reviews, tests)/feature, spec-analyst, security-auditor, settings.json
backend/.claude/How to write backend code specifically"every list endpoint must paginate like this"
frontend/.claude/How to write frontend code specifically"forms use react-hook-form + Zod like this"

The backend and frontend folders were there first. The root one was added for the workflow so the process rules aren't copied into both packages. The pipeline's backend-dev agent (root) is told to read backend/.claude/agents/hono-builder.md for the detailed rules, so the two layers work together.

How Claude Code reads them

  • Start Claude from the repo root (cd ~/codes/ERP-diecast && claude). It loads the root CLAUDE.md, root settings.json, root agents and root skills.
  • Package files load when relevant. Claude reads backend/CLAUDE.md when it works on backend files, and it discovers backend/.claude/skills for work under backend/. You saw these listed as "from backend/.claude/skills".
  • Worktrees contain their own copy of all of this, because a worktree is a full checkout. That's why, while PR #1's worktree existed, /context listed skills twice (once from your folder, once from the worktree). Removing the worktree removes the duplicates.
  • A branch's .claude files apply to that branch. If an agent changes an agent file on its branch, only that worktree sees the change until it's merged.

settings.json in one paragraph

It lists commands Claude may run without asking (allow: git on feature branches, gh pr, bun, docker compose up…) and commands that are always refused (deny: force-push, pushing to main, gh pr merge, rm -rf, reading .env). On GitHub Free you can't lock main on the server, so these deny rules and your habit of merging only green PRs are the safety net.

Chapter 11

The agent pipeline

An agent is a Claude instance with a specific job and instructions (a file in .claude/agents/). A subagent is an agent started by your main Claude session to do one task and report back. A skill is a saved procedure you trigger with a slash command, like /feature.

flowchart TB
  You(["You"]) -->|"/spec, /freeze"| Coord
  Coord["Coordinator
your main Claude session (Opus)"]
  Coord -->|brief| EX["explorer (Haiku)
finds code"]
  Coord -->|brief| TW["test-writer (Sonnet)
tests from rules"]
  Coord -->|brief| BE["backend-dev (Sonnet)"]
  Coord -->|brief| FE["frontend-dev (Sonnet)"]
  Coord -->|brief| RV["4 reviewers (Sonnet)
code · security · performance · spec"]
  Coord -->|brief| TR["test-runner (Haiku)
runs all checks"]
  EX & TW & BE & FE & RV & TR -->|report| Coord
  Coord -->|"push + PR"| GH[("GitHub")]
  GH -->|"your comments"| Coord
Hub and spoke: agents never talk to each other directly. The coordinator hands each one a written brief and reads its report. Everything is saved in .pipeline/<feature>/ on the feature branch, so work can resume in a new session.

The loop

  1. Specyou spec-analyst

    /spec grn: Claude compares with how mature ERPs handle GRN, asks you questions, writes docs/specs/grn.md with numbered rules and questions for the factory.

  2. Freezeyou

    /freeze grn: checks the spec is complete and locks it. From here the agents take over. New ideas go to the backlog, not into the build.

  3. Buildagents

    /feature grn: creates feature/grn in a worktree, writes failing tests from the rules, builds backend then frontend until tests pass.

  4. Verifyagents

    Four reviewers check code quality, security, performance and "does it match the spec". Test-runner runs everything. Problems go back to the right developer agent; the loop repeats (max 3 times, then it asks you).

  5. PRagents GitHub

    Pushes the branch, opens a PR with a summary and a manual test checklist, waits for CI to be green.

  6. You test and decideyou

    Follow the checklist in the browser. Merge, or leave comments. /loop 10m /watch-prs picks up comments and runs the fix loop again.

Chapter 13

What if…

…I just want to push straight to main like before?

Git will let you (GitHub Free can't block it on a private repo). But then CI only checks after the code is already on main, and the agents' work and yours can clash. For a one-line typo it's harmless; for anything real, use a branch and a PR. It adds about two minutes.

…CI is red on my PR?

Open the PR → Details on the red job → click the red step. The last lines say what failed: a file and line for type/lint errors, a test name for failing tests. Fix on the same branch, commit, push. CI re-runs by itself. For formatting errors, bunx biome check --write . usually fixes them automatically.

…GitHub says "This branch has conflicts"?

A merge conflict means main changed the same lines your branch changed, and git can't decide which to keep. To fix:

$ git switch feature/x
$ git pull origin main          # bring main's changes into your branch
  git marks conflicting spots in files like this:
  <<<<<<< yours … ======= … theirs >>>>>>>
  edit each spot to the correct final version, delete the markers
$ git add -A && git commit
$ git push

Or ask Claude: "resolve the merge conflicts on feature/x with main". It's routine work.

…I edited files in my main folder while on main, and I wanted a branch?

Uncommitted changes move with you. Run git switch -c feature/x before committing, and your edits are now on the new branch, with main untouched.

…I want to throw away a branch or a worktree?

git worktree remove <folder> (refuses if there's uncommitted work: that's a safety check; look with git -C <folder> status first), then git branch -D <branch> (capital D deletes even if unmerged) and git push origin --delete <branch> for the GitHub copy.

…the pipeline stops and asks me something?

That's by design. It only stops when the spec doesn't answer a question, or when the fix loop ran 3 times without success. Answer it; the answer is written into the spec so it's never asked again. Repeated stops usually mean the spec needs more detail.

…I don't understand what an agent did?

Everything is on the branch: the PR's Files changed tab shows the code, and .pipeline/<feature>/ has the plan, each agent's report, all review findings and the questions asked. You can also ask Claude "explain this PR to me".

…something in this handbook is out of date?

The source of truth is the repo: CLAUDE.md, docs/WORKFLOW.md, .claude/ and .github/workflows/ci.yml. Ask Claude to update this handbook when the workflow changes.

Chapter 14

Glossary

Agent Claude
A Claude instance with a specific role and instructions, defined in a file in .claude/agents/ (e.g. security-auditor).
Acceptance criterion Spec
A "Given … When … Then …" sentence in a spec that describes a testable outcome. Each one becomes a test.
Backlog Docs
List of deferred work, bugs and ideas in docs/backlog.md, each with a permanent id like BL-014.
Base branch Git
The branch a PR wants to merge into, usually main (or an epic/… branch for epic parts).
Biome Tooling
The linter and formatter used in both packages (instead of ESLint/Prettier). bun run lint checks; bunx biome check --write . fixes what it can.
BR (business rule) Spec
A numbered, testable rule in a spec, e.g. BR-GRN-04. Numbers are never reused.
Branch Git
A named line of commits. Work on a branch doesn't affect main until it's merged.
Branch protection GitHub
